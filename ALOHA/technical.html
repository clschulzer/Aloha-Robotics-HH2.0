02 / THE PLANNING CORE

An empty slot
is only one input.

The current platform uses a deterministic scheduler. It is not a trained emergency predictor or an LLM. The “agentic” architecture is a proposed layer around explicit rules.

  1. Find a candidate. findWindow scans in fixed time steps, checks planned cases and alarm blocks, and reserves preparation and rollback margins.
  2. Check the evidence. Missing plan or usage data produces no proposal. Sparse history is rejected rather than interpreted as availability.
  3. Keep the fleet usable. fillGaps prioritises deadlines, limits daily update bookings and assigns a replacement device. It also accounts for robot bookings.
  4. Replan a changed window. reschedule reruns the rules after an alarm block while respecting other planned robot jobs.

What “risk” means in this version

windowRisk takes the highest hourly share of historical use inside a proposed window. That is a lower bound for use at any point in the entire window, not a calibrated probability that the whole update will finish undisturbed. The sample history and thresholds are invented.

A rule engine is a useful foundation, not a clinical validation. For example, the current replacement-device selection filters outage and update conflicts; it does not fully establish procedure compatibility or check every planned use of the substitute.

The development specification separates a hard rule core, an optimiser, a usage model and an LLM for explanation. It also records gaps in the current planner and proposed evaluations.

03 / THE START DECISION

The suggestion
doesn’t get the final say.

The detailed demo routes start attempts through canStart. It rejects an update if any of these conditions applies:

  • The update involves arm movement and needs supervised on-site service.
  • Medical-physics clearance or the local “surroundings clear” confirmation is missing.
  • The device is in use or an alarm has blocked the window.
  • The package is unchecked or has been recalled.

The interface demonstrates role-specific decisions. In the browser these are local flags, not authenticated clinical approvals. Production would need verified identity, fresh device and alarm state, audit records and enforcement at the actual start boundary.

Source: canStart in planner.js. A proposed AI helper cannot override these rules; plugging in must not stand in for a human start decision.

04 / THE PROPOSED ARCHITECTURE

Connect the information.
Then the last metre.

The architecture sketches a local clinical coordination layer between hospital operations, manufacturer services, people and mobile equipment. These are design proposals, not deployed integrations.

IN

Hospital + manufacturer

Procedure timing, equipment need, staff roles, alarms, software state, packages and recalls.

01

Clinical coordination node

Device record, calendar and fixed rules. Helpers propose windows, route requests and explain decisions.

✓

Human decision

Responsibility, clearance, local surroundings check and explicit start confirmation.

02

Companion or robot

A proposed physical bridge for power, data and observations at an otherwise disconnected C-arm.

↶

Result + evidence

Version, status and approved log data return to the team. Failures require a visible service path.

Keep responsibilities separate

The device’s update mechanism stays responsible for installation and recovery. The coordinator helps arrange a suitable moment and tracks the outcome. A robot is one possible way to deliver power and data; the first pilot can begin with people performing that step.

Design for the actual hospital

The proposal minimises data to room, time and equipment need, plus role, shift and area. It anticipates intermittent connectivity, retained packages and logs, and hospital-approved data flows. Sites that prohibit connectivity require an authorised on-site service route.

05 / THE NEXT BUILD

Start with evidence.
Earn the next step.

  1. Validate the data contract. Establish which software, usage, location and error signals are actually available and permitted.
  2. Run a human-assisted pilot. Test whether clear ownership and good timing improve update completion before adding autonomous hardware.
  3. Evaluate the planner. Use representative schedules, emergency cases and stale-data scenarios. Validate substitute-device suitability and the complete start boundary.
  4. Test the physical bridge. Measure supply needs, access to plugs and ports, cable hazards and confirmation behavior with a training system.
  5. Close failure paths. Prove how failed or interrupted updates are detected, recovered and handed to service.
