# Research and design review — Constellation

Checkpoint: `0f0addb`. Before this version, GitHub was fetched and Claude's PR #9 was reviewed and merged. It adds only `OPUS/christian/`. The original source folders remain intact.

## What changed from the earlier attempts

The goal here is maximum animation craft without turning the stage into a dashboard:

1. A phone rotates into a physical resting position, then travels to one side for the character walkthrough. The same object persists; it is not a new card layout on every click.
2. The theatre board has perspective only during its entrance. It becomes flat before anyone must read it.
3. Scouts evaluate real candidates. Candidate conflicts and acceptable results cause small, brief feedback rings. Their trajectories remain inside the future portion of the day.
4. The first gold window fractures when the trauma reservation arrives. This is cancellation of a proposal, never interruption of an installation.
5. The next search produces an alternative from the same model. The screen does not change the answer by swapping a hardcoded text label.
6. The architecture grows in dependency order. The node appears at arrival. Small upper-side sprouts add texture without occupying the labels.

## What I learned from OPUS

Its strongest effects are local and causal: a tap lands on a control, a line delivers a pulse, a node reacts to that arrival. The poor version of “fungus” is a decorative mass of moving lines. The useful version is a small number of paths that tell the viewer where to look next.

This build uses OPUS audio/particle primitives and the actual OPUS v2 scoring module, while replacing the stage choreography. The enlarged swarm and dimensional entrances are new; the film, characters and rules belong to the team.

Christian's newly merged version confirms the important story order: feeling responsible → priority → an opportunity from hospital data → a human → help → a returned result. It also explicitly documents the conflicting “18 minutes” source. This build follows the team's 120-minute rule core, with recovery margin, and avoids an invented update-speed benefit.

## Evidence and boundaries

The interviews establish that mobile systems are often off and unplugged, availability is uncertain, and software updates require a human decision. Mechanical calibration is a separate supervised process.

The scorer implements hard rejection followed by illustrative ranking using unplanned-use history, emergency arrival assumptions and a previous-case overrun factor. Those inputs are synthetic. Independence assumptions and the probability calibration have not been clinically validated. The browser code is real; the clinical forecasting claim would not be.

The live device service interface, power supply, docking and robot control remain integration work. Verification returns a result to the responsible team; it does not automatically grant clinical release.

## Review corrections

The first visual review found lines crossing the human and device captions. Those paths were routed around the labels, and decorative growth was restricted to the upper side of nodes. Calendar case padding was tightened so the second text line stays inside each block. The final signature was moved away from the flowing background.

The final full rehearsal also measures actual scorer calls and delivered frame rate by scene. A first rehearsal exposed redundant text/style writes during the gold-window hold; those were replaced with change-only writes, and invisible converged scouts stop integrating their motion. Performance is checked in the browser, not inferred from a still image.

## Rendering correction and team checkpoint

The focused Firefox comparison isolated the calendar slowdown to a persistent perspective/compositing layer. With the same 144 scouts, the measured scene changed from 23.6 fps to 59.2 fps when flattened, and 60.1 fps with a separate canvas layer. The production code retains perspective only for the entrance, then removes it. The final full rehearsal includes this correction.
