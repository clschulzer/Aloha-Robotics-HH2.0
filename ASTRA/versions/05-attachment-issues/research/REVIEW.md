# Design and source review — Attachment Issues

## Fresh repository checkpoint

This version began after fetching main at `fbff4870b0b847f7a83ba25b49cb43eef84fdf8f`. No open pull requests remained at that checkpoint. The preceding version had reviewed and merged Claude's OPUS v3 and comparison-gallery changes.

The new OPUS v3 character, calendar, night and morning scenes were rendered in Firefox. Its coherent night-to-morning story is a useful lesson: a scene becomes more legible when motion advances one idea instead of decorating every surface. This version applies that lesson to a different story, the machine's demanding personality.

Christian's latest storyboard was also reread. Its distinction between *priority* and *opportunity* is retained: a hungry or disconnected character does not choose a maintenance time. Hospital data and scheduling rules do.

## Decisions

- Keep the complete original movie. Its ending supplies the energy for the short ember title; the next frame changes to a warm, quiet character composition.
- Give the audience one joke to read. The portrait and state occupy separate areas. There is no simultaneous dashboard, phone screenshot and character collection.
- Make recovery the unexpected last joke: “This never happened.” A delayed audit stamp disagrees. Then accelerate the existing faces and use the fast CRT collapse.
- Use the familiar visual grammar of a theatre timetable. Case blocks, turnover, a cancelled case, a reserve row and a backup chip tell the scheduling story before the speaker explains the rules.
- Animate scouts with spring motion, but clear them away from the result. Each arriving scout performs a candidate evaluation. Activity has a purpose.
- Grow four service connections in sequence. The next node enters when the traveling tip arrives; a single outside return path closes the loop.
- Use the actual authorization predicate behind the human-thumb joke. A pending state cannot start merely because a comic cursor arrives.
- End with a solution in human terms. A quiet, oversized closing line replaces a final technical dashboard or another gag.

## Boundaries preserved

The source film, character art, deterministic planner and case-data model are reused. The hospital calendar data is illustrative. The proposed robot and data connection are presented as proposed. A simulated receipt is not a clinical release.

The new OPUS v3 material contains illustrative confidence and overnight-outcome language. This version does not promote those examples into validated clinical probabilities or a guarantee that every system is ready by morning.

The code tests responsibility and timing, not a claim that a C-arm has become autonomous. The speaker explicitly distinguishes the browser prototype from the integration still to be built.

## Visual corrections during review

The first complete cue review exposed a return path crossing the Find caption. It was routed around the outside of the diagram. The phone's pending title was changed from “Cio is ready” to “Cio needs care,” so the waiting state does not imply clearance. A tiny receipt footer was removed.

The phone now stays visible between waiting and approval. Its simulated thumb targets the button's measured position, rather than a guessed coordinate. Repeated connections do not redraw while the presenter describes the authorization gate.
